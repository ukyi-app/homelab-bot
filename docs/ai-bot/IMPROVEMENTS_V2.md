## 요약

**가장 먼저 할 일은 멈춤 해소다.** `unknown` 작업 하나가 봇 전체를 세우고, 배포만으로도 그 상태가 생길 수 있다. 실행 중 들어온 새 메시지를 반영하는 기능(2-4)도 이 문제를 푼 뒤에만 안전하다.

**새로 더할 핵심은 넷이다.**

1. 수신·진행 신호는 모델이 아니라 게시 서버가 단다(👀, 입력 중 표시, 상태 리액션).
2. owner가 입력을 끝낼 때까지 기다린 뒤 판단한다(입력 중 감지 디바운스).
3. 모델이 서버에 요청을 남기는 규약을 둔다(조회 요청, 예약·감시 요청).
4. 기억은 출처·승인·적용 기간·위계를 갖는다. 시작은 owner의 실제 기록에서 판단 기준을 뽑아 검토받는 것이다.

**이미 갖춘 것이 많다.** 구조화된 전달 규약, 멘션 없는 스레드 추적, 터미널 질문 대기 차단, 출처·만료가 있는 기억 스키마가 이미 있다. 남은 일 대부분은 새로 만드는 것보다 **진입점에 연결하는 것**이다.

**하지 않을 것도 정했다.** 개발 머신에서 에이전트 실행, 전체 대화의 주기적 자동 학습, 10초 이상 고정 디바운스는 1인 owner·격리 우선 설계와 맞지 않는다(§3).

## 0. 설계 전제

homelab-bot은 owner 1명이 Discord로 쓰는 봇이다. 작업자는 k8s sandbox 파드에서 `auth.json` 기반 Codex CLI로 돌고, 권한은 읽기 전용·자격 분리·egress 프록시로 묶여 있다. 우선순위는 "끊겨도 잃지 않고, 틀려도 피해가 작게"다.

그래서 **대화 방식은 적극적으로 개선하고, 행동 범위는 격리 모델 안에서만 넓힌다.**

## 2. 단계별 개선안

### 1단계: 멈추지 않게 (다른 모든 개선의 전제)

#### 1-1. `unknown` 자동 해소와 정상 종료

**문제.** 실행 슬롯이 전역에 하나뿐이라 `unknown` 작업이 남아 있으면 다음 작업을 시작하지 않는다. 문서도 "unknown 해제는 남은 과제"라고 적는다.

**배포가 이 상태를 만든다(코드 확인).** 종료 시 진행 중 작업을 기다리는 상한은 `stopTimeoutMs` 기본 **20초**(`src/main.ts`)다. 대화 시간 예산은 **60초**다. 공유 앱 차트에서 `terminationGracePeriodSeconds`를 찾지 못했으므로 기본 30초가 적용된다. 게시 서버는 digest PR 자동 병합으로 배포되므로, 대화 도중 배포되면 lease가 만료돼 `unknown`이 되고 사람이 풀 때까지 봇이 멈춘다.

**개선.**

- **자동 해소:** 새 게시 서버가 `unknown` 작업에 대해 cancel capability를 발급해 작업자에 확인한다. `stopped:true`면 `failed`로 바꿔 `/retry`할 수 있게 한다. 작업자 파드 재시작(부팅 ID 변경)도 종료 증거로 쓸 수 있다.
- **정상 종료:** SIGTERM을 받으면 새 claim부터 멈추고, 진행 중 작업은 예산 끝까지(60초+여유) 기다리거나 cancel 후 `stopped`를 확인한다. grace period는 약 90초로 늘린다.
- **경보:** `unknown`이 일정 시간(제안: 10분) 넘게 지속되면 알린다.

**2-4와의 관계.** 실행 중인 추론을 중단하는 방식은 취소 확인에 실패하면 곧바로 `unknown`이 되고 전역 정지로 이어진다. 그래서 1-1이 2-4보다 먼저다.

#### 1-2. 레인 분리: read / chat / task

**문제.** `/read`는 작업자도 모델도 쓰지 않지만 같은 스케줄러 슬롯을 쓴다. 모델 작업이 `unknown`이거나 `waiting_user`(한도·인증 만료)면 `/read`도 막힌다. 홈랩을 봐야 하는 순간에 막히는 구조다.

**개선.**

- **1차:** read 레인을 전역 슬롯에서 분리한다. 작업자와 무관하므로 위험이 거의 없다.
- **2차(T18):** task 레인은 별도 작업자·슬롯으로 둔다. 대화의 응답성과 작업의 연속성을 따로 지키기 위해서다. 긴 작업이 도는 동안에도 chat이 답하고, 진행 상황 질문에는 DB의 task 상태로 결정적으로 답한다.

#### 1-3. 관측과 경보

**문제.** `/readyz`는 HTTP와 DB만 본다. 토큰 401이나 fatal close로 Gateway가 영구 중단돼도 파드는 Ready다. 알아챌 수단은 외부 healthchecks ping 하나뿐이다. 지표는 3개이고 scrape도 미연결이다.

**개선.** job 상태별 개수(`unknown`·`waiting_user`·대기열), gap 개수와 최장 지속 시간, 가장 오래된 outbox, 모델 실행 시간(이미 감사에 남는 `model_timing`을 히스토그램으로)을 내보낸다. 경보 룰은 `unknown` 장기화, `waiting_user`, gap 장기화, Gateway fatal에 건다. 효과 측정 지표도 함께 만든다(§4).

#### 1-4. 작업자 인증 상태

**문제.** 작업자 readiness는 `auth.json`이 일반 파일인지만 본다. 인증 만료는 실제 질문이 실패해야 드러나고, 그 순간 스케줄러가 `waiting_user`로 선다.

**개선.** 모델을 부르지 않는 주기적 인증 확인을 지표로 내보낸다.

**시드 교체 함정.** 시드는 `auth.json`이 없을 때만 설치된다. Infisical 시드를 바꿔도 PVC 쪽은 그대로다. 시드 세대 표식을 두고 세대가 바뀌면 교체한다.

### 2단계: 대화 품질

#### 2-1. 봇이 자기 답을 보게 하고, 긴 대화는 요약으로 잇기

**문제(코드 확인).** `src/store.ts`의 `context()`는 `actor_id = owner`인 이벤트만 가져온다. 봇 답은 `results`에 있지만 문맥에 들어가지 않는다. "가설 2번 더 설명해줘"에 모델은 가설 2번을 모른다.

**개선.** 같은 대화의 최근 `results`를 봇 차례로 끼워 넣고, 32KiB 예산을 owner 메시지와 나눠 쓴다(제안: owner 60%, 봇 40%). 봇 답도 지시가 아닌 자료 칸에 둔다.

**긴 대화.** 스레드가 일정 시간(제안: 6시간) 조용하면 요약을 만들어 두고, 다음 질문 때 최근 20개 창 앞에 붙인다. 20개를 넘긴 긴 스레드도 앞부분 맥락을 잃지 않는다.

#### 2-2. 수신·진행 신호는 게시 서버가 단다

**문제.** slash 명령에는 ACK가 있지만, 일반 메시지에는 답이 게시될 때까지 눈에 보이는 수신 표시가 문서에 없다. 봇이 받았는지, 대기 중인지, 멈췄는지 owner가 알 수 없다.

**개선.** 모델이 문장을 만들기 전에 게시 서버가 신호를 단다.

- **수신 즉시 👀:** 이벤트 저장 직후 단다. 리액션 추가는 멱등이다.
- **모델 실행 중 입력 중 표시:** `POST /channels/{id}/typing`. 표시는 약 10초 유지되므로 실행 중 8초 간격으로 갱신한다.
- **상태 리액션:** ⏳ 다른 작업 뒤 대기, ⏸️ `waiting_user`, ❓ `unknown`, ⚠️ 실패, ✅ 게시 완료.

**효과.** 1-1의 "멈췄는데 아무도 모름"이 owner 화면에 바로 드러난다.

**주의.** 리액션 API는 rate limit이 빡빡하다. 상태가 바뀔 때만 달고, 게시와 같은 정책 재검사를 거친다.

#### 2-3. 입력이 끝날 때까지 기다리기

**지금.** 750ms 기다리며 아직 실행하지 않은 chat job을 새 입력으로 대체한다. 한 요청을 여러 메시지로 나눠 보내면 첫 메시지만 보고 답하기 시작할 수 있다.

**제안.** 기본 2~3초에 owner가 입력 중이면 연장하고, 상한은 15~20초로 둔다(제안값, 실사용으로 조정). `GUILD_MESSAGE_TYPING` intent(2048, 비특권)를 추가해 `TYPING_START`로 연장을 판단한다. 현재 intents `33281`에 더하는 변경이다. `/urgent`는 지금처럼 즉시 처리한다.

**비용.** 첫 응답이 늦어진다. 2-2의 👀가 체감을 보완한다.

#### 2-4. 실행 중 새 메시지가 오면 다시 판단 (조건부)

**실행 중 추론을 바로 중단하는 방식은 위험하다.** 취소 확인에 실패하면 `unknown`이 된다.

**권장: 중단 대신 게시 직전 확인.** 답을 게시하기 직전에 "그 사이 같은 스레드에 새 owner 메시지가 있는가"를 본다. 있으면 그 답을 `superseded`로 두고 새 맥락으로 다시 실행한다. 모델 호출 한 번을 버리지만 취소의 불확실성이 없다. `superseded` 상태는 이미 있다.

**진짜 중단이 필요하다면** 1-1 완료 후, chat 레인에서만, 스레드당 연속 재시작 상한(제안: 2회)을 두고 허용한다. task 레인은 절대 중단하지 않는다.

#### 2-5. 답 형식: 짧게, 위험은 남기고, 안 답해도 되게

**지금.** `AnswerSchema`는 `facts`·`hypotheses`·`unknowns`·`checks` 네 배열(8·4·8·4개, 항목당 500자)이다. Discord 요약은 항목당 350자로 줄인다. 진단에는 좋지만 단순한 질문에는 딱딱하다.

**제안 스키마.**

- `reply`: 짧은 본문, 필수(제안: 600자 상한).
- `risks`: 있으면 반드시 게시한다. 길이 제한으로 잘라내지 않는다.
- `details`: 기존 네 배열. `results`에 저장하고 "자세히" 버튼으로 연다.
- `reaction`: 답 대신 리액션만 다는 경우(확인·동의).
- `noReply`: owner가 메모처럼 남긴 메시지에는 답하지 않는다. 받는 것과 답하는 것을 구분한다.

**품질 기준.** 글자 수만이 아니라 "owner가 이 답만 보고 다음 행동을 정할 수 있는가"를 본다.

**지킬 것.** `SYSTEM_INSTRUCTIONS`의 "현재 근거 없이 정상을 주장하지 않는다"는 유지한다. 장애 진단성 질문은 네 칸 형식을 기본으로 둔다.

#### 2-6. 확인 질문은 Discord 버튼으로

**지금.** 터미널 대기는 이미 막혀 있다(`approval_policy = 'never'`). 하지만 모델이 owner에게 되물을 경로 자체가 없다.

**개선.** 출력에 `question`과 선택지(최대 4개)를 두면 게시 서버가 버튼으로 게시한다. 클릭은 새 이벤트로 저장돼 다음 job이 된다. 기존 버튼 interaction 처리를 재사용한다.

### 3단계: 홈랩을 보고, 시간을 다루는 대화

모델이 서버에 요청을 남기는 규약을 둔다. **모델은 요청만 하고, 실행과 판정은 코드가 한다.**

#### 3-1. 조회 요청 규약

**문제.** 대화 모델은 빈 임시 디렉터리에서 돌고 조회 자격이 없어 홈랩을 볼 수 없다.

**개선.** 출력에 `requests: [{ type: 'read', service, template }]`(제안: 최대 3개)를 둔다. runtime이 카탈로그·정책을 검사해 실행하고, 결과를 `untrusted` 자료로 넣어 한 번 더 호출한다. 모델은 자격·URL·쿼리를 만지지 않는다.

**전제.** 로그는 외부 입력이 섞인 텍스트라 인젝션 통로다. **6-1(셸·인증 파일 분리)을 먼저 끝낸다.**

#### 3-2. 예약·감시 요청

**형태.** "롤아웃 끝나면 알려줘", "10분 뒤 Argo 상태 다시 봐줘"를 서버에 맡겨 두고, 모델이나 owner가 시간을 세며 기다리지 않게 한다.

- `/watch service template until:ok within:30m` 명령, 또는 모델 `requests`의 `type: 'watch'`.
- 조건 판정은 코드가 한다(예: 상태 == ok). 모델 호출이 없어 비용이 없고 결과가 결정적이다.
- `src/briefing.ts`의 schedule·lease를 재사용한다.
- 상한(제안): 활성 감시 5개, 최대 24시간, 간격 30초 이상.

#### 3-3. 카탈로그 데이터화 + RBAC 축소

**문제.** 카탈로그에는 봇 자신 하나뿐이고, 서비스를 추가하려면 코드를 고쳐야 한다. 반대로 RBAC는 클러스터 전체 pods·events·nodes 등을 읽을 수 있어 카탈로그보다 넓다.

**개선.** 템플릿 종류(deployment·statefulset·argocd·메트릭·로그)는 코드에 고정하고, 대상(namespace·이름)은 `RUNTIME_POLICIES`에서 스키마로 검증한다. 같은 목록으로 namespace Role과 `resourceNames`를 생성해 RBAC를 좁힌다.

### 4단계: 기억 연결 (`memory.ts` 기반)

#### 4-1. 문맥 주입과 위계

**이미 있는 `kind`와 `status`로 바로 시작할 수 있다.** 순서는 다음과 같다.

1. 정책(`RUNTIME_POLICIES`, 코드): 기억으로 바뀌지 않는다(이미 보장).
2. owner가 확정한 `decision`(4-5의 판단 기준 포함), 유효기간 안의 `preference`.
3. `configuration`: 관측 시각과 재확인 기한을 함께 표시.
4. `incident`.
5. `candidate`: `unverified` 표시.

`search()`로 찾은 기억을 이 순서와 라벨로 넣는다. 기억도 지시 칸이 아닌 자료 칸에 둔다.

#### 4-2. 기억은 모델이 제안하고 owner가 확정

- **명시 저장(`/remember`):** 현재 규칙(출처 확인 + 충돌 없음이면 `active`)을 따른다.
- **모델 제안:** 출력의 `memoryCandidates`는 항상 `candidate`로 저장한다. 스레드에 ✅·✏️·❌ 버튼을 달고 owner가 ✅하면 `active`로 올린다.
- **이유:** 링크가 있어도 해석은 틀릴 수 있다. `memory.ts` 주석도 "출처 링크가 있다고 정확하다는 뜻은 아니다"라고 적는다.
- **인젝션 차단:** `untrusted` 자료(로그·경보·webhook)를 본 실행에서 나온 제안은 `candidate`로 고정하고 표시한다. 주입된 지시가 기억에 눌러앉아 이후 판단을 바꾸는 것을 막는다.

#### 4-3. 조용해진 스레드 정리

2-1의 스레드 요약을 만들 때 기억 후보도 함께 제안한다. 출처는 해당 job과 메시지다. 대화는 `active`로 두어 다음 메시지에 바로 이어진다.

**전체 대화를 주기적으로 자동 학습하지는 않는다.** owner가 한 명이라 자동 수집의 이득보다 승인 부담이 크다.

#### 4-4. 지시의 적용 기간

**이미 있다.** `preference`는 `expiresAt`·`endCondition`이 필수다.

**대화 모드에도 쓴다.** "/quiet 1h", "이 스레드에선 짧게" 같은 지시를 범위(채널·스레드)와 만료가 있는 `preference`로 저장한다. 임시 지시가 의도보다 오래 남아 정상 응답을 막는 사고를 구조로 막는다.

#### 4-5. 판단 기준 문서: 실제 기록에서 뽑고, owner가 틀린 것부터 고친다

**목적.** 4-1의 2순위(owner 확정 판단)를 채우는 출발점이다. 기억이 하나씩 쌓이기를 기다리지 않고, owner가 이미 남긴 기록에서 운영 판단 기준을 한 번에 뽑는다.

**재료.** 봇 `docs/ai-bot/DECISIONS.md`, 플랫폼 설계 문서, `PLAN.md`, owner의 PR 리뷰 댓글과 커밋 메시지.

**형식.** 기준마다 네 가지를 붙인다.

- **통과 조건:** 무엇이면 진행해도 되는가.
- **멈춤 신호:** 무엇이 보이면 멈추고 owner에게 묻는가.
- **충돌 시 우선순위:** 다른 기준과 부딪히면 무엇을 앞에 두는가.
- **근거 링크:** 누가, 언제, 어디서 그렇게 판단했는가.

**검토.** 문서를 스레드에 올리고 "틀린 것부터 짚어 달라"고 요청한다. 잘못 읽은 것, 기준이 아닌데 기준처럼 적힌 것을 먼저 걸러 낸다. owner가 확인한 항목만 `decision`으로 확정한다.

**근거 처리 주의.** `memory.ts`에서 PR 댓글은 `external`이라 근거로 세지 않는다. 그래서 PR 댓글에서 뽑은 기준은 owner가 Discord에서 확인한 메시지가 `conversation` 근거가 돼야 `active`가 된다. `DECISIONS.md` 같은 저장소 문서는 `document` 근거가 되지만, 해석이 틀릴 수 있으므로 모델이 뽑은 기준은 모두 4-2처럼 후보로 두고 owner 확정을 거친다.

**갱신.** 새 결정(DECISIONS.md 추가, 새 리뷰)이 생기면 영향받는 기준만 다시 후보로 제안한다. 각 기준에 `recheckAt`을 두어 오래된 기준을 주기적으로 다시 확인한다.

### 5단계: 작업 레인(T18)을 열 때의 원칙

#### 5-1. 행동 위험 등급

통제 수준은 실패했을 때의 영향 범위와 되돌릴 수 있는지로 정한다.

| 등급 | 예 | 처리 |
| --- | --- | --- |
| 조회 | `/read`, 로그 | 자동 |
| 제안 | 브랜치·PR 생성, 리뷰 댓글 | 자동 실행, 병합은 사람 |
| 되돌리기 어려움 | 클러스터 직접 변경, 비밀 값, force push | 봇은 하지 않음. GitOps PR로만 |

homelab의 GitOps(변경은 PR → Argo CD)가 이미 "제안까지만"이라는 경계를 준다. 봇 행동도 이 경계 안에 둔다.

#### 5-2. 작업은 대상 저장소를 기준으로 시작

sandbox 작업 공간에 대상 저장소를 고정 커밋으로 받아, 그 저장소의 지침 파일(AGENTS.md 등)을 읽고 시작한다. 대화 맥락을 다시 설명하는 대신 프로젝트의 규칙을 그대로 쓴다. egress 허용 목록에 `codeload.github.com`이 이미 있다.

**주의.** PR 리뷰라면 지침 파일은 PR head가 아니라 **기준 브랜치 버전**을 읽는다. PR이 바꾼 지침 파일로 리뷰어를 조종하는 인젝션을 막기 위해서다.

#### 5-3. 완료 보고와 개입 요청 분리

**지금.** `allowed_mentions.parse=[]`라 어떤 게시물도 멘션으로 owner를 부르지 않는다.

**개선.**

- **완료 보고:** 스레드에 조용히 게시한다.
- **개입 요청**(`waiting_user`, 위험 판단, 승인 필요): `allowed_mentions.users=[owner]`로 owner만 호출한다. critical은 Telegram 경로도 쓴다.
- **진행 관찰:** task 실행 중 `--json` 이벤트에서 단계 종류만 뽑아 DB에 남기고 `/status`로 보여 준다. 실행 화면을 직접 열지 않고도 진행을 볼 수 있는 경로이며, 원문 내용은 넣지 않는다.

#### 5-4. 전용 신원

PR·댓글은 owner 계정이 아닌 전용 GitHub App으로 남긴다. 배포 App 패턴이 이미 있다. 감사와 권한 회수가 쉬워진다.

### 6단계: 보안 정리 (모델 전환 전에)

#### 6-1. 셸·인증 파일 분리: 지침이 아니라 실행 단계에서

**지금.** `SYSTEM_INSTRUCTIONS`에 "셸·도구·운영 변경을 실행하지 않는다"고 적혀 있다. 그러나 이것은 지침이다. 실행 단계에는 도구 예산 8회가 있고, 같은 UID라 모델 셸이 `auth.json`을 읽을 수 있다(`bot-architecture.md` §6.4).

**원칙.** 막아야 할 것은 지침이 아니라 실행 단계에서 막는다.

**선택지.**

- (a) chat 레인은 도구를 완전히 끈다.
- (b) 인증 자격을 별도 UID나 사이드카 프로세스로 분리한다.
- (c) 모델 API를 직접 호출한다.

**이전 안 수정.** 이전에는 (c)를 권했다. 구독 인증 유지가 비용상 맞다면 **(a)+(b)**가 현실적이다. 단, 구독 인증을 무인 봇에 쓰는 것이 공급자 약관상 허용되는지는 별도로 확인해야 한다.

#### 6-2. 나머지 보안·운영 항목

- **게시 서버 egress:** 사설 대역을 뺀 모든 공인 IP의 443이 열려 있다. Discord 토큰·DB·클러스터 조회 토큰을 가진 프로세스이므로 egress 프록시와 SNI 허용 목록(Discord, healthchecks)으로 좁힌다.
- **공개 webhook 경로:** 공유 차트가 공개 host에 `/` 전체를 쓰므로 클러스터 안에서 Traefik을 거쳐 `/readyz`·`/metrics`에 닿는다. ingress를 `/github`로 좁히거나 metrics를 별도 포트로 옮긴다.
- **마이그레이션 권한:** Job이 앱 env 자격 전부를 받고, 같은 DB 역할이 DDL까지 한다. Job에는 `DATABASE_URL`만 주고 마이그레이션 역할과 런타임 역할(DML만)을 나눈다.
- **DB TLS:** `sslmode=require`는 서버 인증서를 검증하지 않는다. `verify-full`과 클러스터 CA로 바꾼다.
- **버전 어긋남:** 게시 서버는 자동 배포, 작업자는 사람 PR이다. 작업자가 `/readyz`로 계약 버전을 알리고 게시 서버가 확인한다. 배포 봇이 작업자 digest PR도 자동 생성하고 병합만 사람이 한다.
- **경보 경로 시험:** 봇 route를 켤 때 Telegram 형제 route를 함께 켜야 한다. CI에서 `amtool config routes test`로 critical 경보가 Telegram에 도달하는지 검사한다.
- **조용히 버려지는 전송:** ID 없는 outbox `unknown`은 24시간 뒤 `blocked`가 된다. 스레드에 "전송 확인 실패, 재전송" 버튼을 남긴다.
- **해제 수단 없는 gap:** 복구 한도(100건×10쪽, 30초)를 넘은 gap은 수동 판단 대상인데 해제 명령이 없다. 상태 확인과 명시 해제 명령을 감사와 함께 둔다.
- **데이터 보존:** 코드 검색으로 `events`·`results` 정리 로직을 찾지 못했다(기억 삭제만 있음). owner 메시지가 무기한 쌓이는지 확인하고 보존 기간을 정한다.

## 3. 하지 않을 것

**개발 머신에서 에이전트 실행(터미널 탭 방식 등).** 사람이 실행 화면을 직접 열어 볼 수 있는 장점은 크지만, 개발 머신의 넓은 자격이 sandbox 격리 모델과 충돌한다. 작업 관찰은 5-3의 진행 기록으로 대신한다. owner가 직접 시작한 작업만 개발 머신으로 보내는 별도 경로는 검토할 수 있지만, 봇에서 개발 머신으로 가는 신뢰 경계를 새로 설계해야 한다.

**10초 이상 고정 디바운스.** 장애 대응용 봇에는 길다. 입력 중 감지로 짧게 가져간다(2-3).

**전체 대화의 주기적 자동 학습.** 1인 사용이라 승인 부담이 이득보다 크다. 스레드 요약 때 후보를 제안하는 것으로 충분하다(4-3).

**사람 같은 계정과 문체 학습.** owner 한 명의 선호는 `preference` 몇 개로 충분하다. 다만 PR·댓글용 전용 신원은 둔다(5-4).

## 4. 효과 측정

| 확인할 것 | 지표 |
| --- | --- |
| 대화의 연속성 | 같은 스레드의 `/retry`·재질문 비율, 답에 단 👎 리액션(`GUILD_MESSAGE_REACTIONS` intent 1024 필요) |
| 판단 부담 | 개입 요청 수와 그중 실제로 필요했던 비율 |
| 기억과 행동의 오류 | 기억 정정·삭제 수, 후보 거절률, 판단 기준 문서의 수정 항목 수 |
| 운영 비용 | 첫 신호(👀)까지 시간, 답 게시까지 시간, `model_timing`, `waiting_user` 진입 횟수, `unknown`으로 멈춘 시간 |

## 5. 실행 순서

1. **실가동:** 실제 작업자 이미지·명령, 모델 호스트 egress, 인증 시드, 경보 route와 Telegram 형제 route(`bot-architecture.md` §8의 남은 일).
2. **1단계:** 1-1 `unknown` 자동 해소·정상 종료, 1-2 read 레인 분리, 1-3 지표·경보.
3. **체감이 큰 작은 변경:** 2-1 봇 답 포함, 2-2 수신 신호, 2-5 답 형식.
4. **6-1:** 셸·인증 분리.
5. **3-1·3-2, 2-3·2-4:** 조회·감시 요청, 디바운스, 게시 직전 재판단.
6. **4단계:** 기억 연결, 4-5 판단 기준 문서.
7. **5단계:** 작업 레인(T18).

**의존 관계.** 2-4(진짜 중단 방식)는 1-1 뒤에만 가능하다. 3-1은 6-1 뒤에만 안전하다. 4-2의 "untrusted를 본 실행은 후보 고정"은 3-1이 들어올 때 함께 넣는다.
