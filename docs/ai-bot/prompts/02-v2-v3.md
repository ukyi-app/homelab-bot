## 1. 버전별 목표·순서

| 버전 | 목적 | 진입 조건 | 완료 기준 |
|---|---|---|---|
| **V2** | **변경 전후를 검증하고 후속 일을 챙기는 봇** | V1의 필수 기능·경계·실제 시험 상태를 확인; 누락은 별도 처리 | 변경→검증→후속→회고의 증거 연결; 의도한 장애 검출 및 리비전 정합 |
| **V3** | **미리 점검하고 개선을 제안하는 봇** | V2 완료 근거 + 실제 사용자 피드백·관측 범위 확보 | 근거 있는 유용한 개선 제안, 오탐·반복 감소, 미확인 경계 유지 |

V1에서 제공한 기본 버전/배포 상태 조회는 V2의 실제 기능 검증과 다르다. **V2에서도 자동 재시작·배포·롤백·DB 수정 권한은 부여하지 않는다.** V3는 더 많은 시스템을 조회할 수 있더라도 임의 외부 스캔·관리 권한 확대를 허용하지 않는다.

# PART A. V2: 검증과 후속 관리

## V2-01 + V2-11. 배포 후 기능 검증과 리비전 연결: 가장 먼저

**사용 예:** “방금 병합한 PR의 변경이 실제 서비스에 반영됐고 정상 동작하는지 확인해 줘.”

**입력:** 서비스·환경·PR·검증 대상·승인된 엔드포인트·관측 시간창. **허용:** 등록된 상태/기능 점검·지표 비교. **금지:** 배포·임의 외부 요청·쓰기 기능 테스트·자동 롤백. **완료:** 읽은 이미지·설정·커밋이 실제 배포와 연결되고 검증 범위가 명시됨.

- 리뷰 `head_sha`, 실제 merge commit(또는 병합 결과), 배포 설정 커밋, GHCR 이미지 digest, Argo/Kubernetes 상태를 근거 있는 그래프로 연결한다. 이 연결이 불분명하면 옛 PR 테스트를 실제 배포 성공 증거로 사용하지 않는다.
- 등록한 상태/조회 전용 테스트와 오류·지연·자원 추세를 확인한다. GET도 부작용이 있는 엔드포인트일 수 있으니 사전 승인된 안전한 점검 API만 사용한다.
- 비교 시점·트래픽·기준선·수집 누락을 표시하고, 배포 완료 / 기능 검증 통과 / 관측 불충분 / 이상 발견을 분리한다.
- V1의 기본 배포 확인 결과를 재활용하되 **서비스 기능, DB 쓰기, 성능 회귀**를 별도 증거 없이 통과 처리하지 않는다.

> 참고: 새 플랫폼의 Argo CD는 공개 webhook 없이 60초 폴링으로 Git 변경을 읽는다(`timeout.reconciliation: 60s`, `timeout.reconciliation.jitter: 0`. 확정(사용자 2026-10-18, T05), 설계 F "추가 확인"). 그래서 main 병합에서 배포 시작까지 최대 약 1분 늦어진다(설계 A.4 3번). 병합 직후의 Argo CD 상태를 새 리비전의 결과로 읽지 않도록, 배포 연결과 관측 시간창은 이 주기를 감안해 잡는다.

**시험:** 오래된 head·다른 환경/이미지·잘못 연결된 배포/커밋, 의도적 HTTP 오류·타임아웃·지표 누락·불충분한 기준선, 동시 배포와 업데이트. 잘못된 과거 성공이 현재 결과를 덮지 않아야 한다.

## V2-02 + V2-03. 변경 영향 분석과 CI 실패 진단

**사용 예:** “이 PR이 영향 주는 서비스와 rollback 조건 알려줘.” / “`ci`가 왜 실패했어?”

- 변경 파일·공유 Helm 차트·서비스 의존 관계·DB 마이그레이션(Argo CD Sync hook Job, 이미 self-migration인 앱은 그 방식)/expand-contract·스키마 호환·설정 리비전을 근거로 영향 범위, 가능한 재시작·중단, 사전 시험, 되돌리기 가능 조건을 정리한다. 근본 원인을 증명하지 못하면 추정이라고 명시.
- CI 로그는 실패 단계·관련 변경·검증한 재현 여부를 구분하고 PR·로그의 지시문을 실행하지 않는다. 필요 시 수정안/PR은 V1 변경 작성 권한 경로를 재사용한다.
- AI 리뷰 → 수정 → 다시 리뷰의 무한 반복을 막는 횟수·변경 내용·종료 조건을 둔다.

**시험:** 공유 파일 변경, 호환성 조건 미확인, 특정 테스트만 실패, 거짓 CI 로그 지시, 수정 루프·동일 지적 반복, 허용 범위 밖 수정 거부.

## V2-04. 알림 기반 읽기 전용 자동 조사

**사용 예:** “DB 연결 실패 경보가 뜨면 관련 지표와 최근 변경을 먼저 조사해 줘.”

- 플랫폼 Alertmanager의 그룹화·중복 억제를 최대한 재사용한다(경보는 receiver `bot`의 webhook으로 클러스터 안 봇 Service에 온다). 허용한 알림 유형/서비스만 사건 ID로 묶어 자동 조사.
- 사건별 동시 실행·재조사 주기·수명·비용 상한 적용. 반복 알림 폭주 시 같은 사건을 중복 조사하지 않음.
- 조사 결과는 확인된 사실 / 추정 / 미확인 / 다음 확인으로 제공. 자동 재시작·임의 수정 금지.

**시험:** 경보 폭주·동일 원인의 다중 알림·오탐·관측 데이터 없음·미등록 서비스·호스트 단절.

## V2-05 + V2-06. 조건부 예약·미해결 항목·주간 요약

**사용 예:** “PR이 병합되면 배포 확인해 줘.” / “내일 저녁에도 해결 안 됐으면 알려줘.”

- V1의 durable 예약/작업 기록을 재사용. 조건형 작업에는 요청자, 조건, 대상, PR/리비전, 발효·만료, 취소 여부, 권한, 중복 키, 실행 결과 보관.
- 이벤트 역순·지연·재시도·재시작·권한 철회·새로운 배포가 옛 조건을 무효화하는 경우를 처리한다. 예약 당시에 허용됐더라도 실행 직전 권한 재확인.
- 미해결 사건·답변 대기·보류 PR·점검 항목 관리. 조용한 시간은 알림 정책이지 상태 삭제가 아니다. 주간 브리핑은 중요한 변화와 다음 행동 위주.
- 예약된 상태 확인이 곧 미래의 운영 쓰기 권한을 주지는 않는다.

**시험:** 취소 후 도착 이벤트, 만료된 조건, 다른 PR/head 이벤트, 권한 회수, 재시작·ACK 유실·중복 예약, 다중 시간대.

## V2-07 + V2-09. 장애 회고·재발 방지·오래된 기억

**사용 예:** “이번 장애 정리하고 다음에 안 생기게 검사 PR 제안해 줘.”

- 시간순 사실, 실행한 조치, 결과, 추정 원인, 미확정 사항, 재발 방지·운영 문서 변경 후보를 구분한다. 조치 후 호전 = 근본 원인 증명이 아니다.
- 런북/결정 문서/테스트·이슈·변경 PR은 V1의 승인된 경로로 제안. 읽지 못한 로컬 런북을 실재하지 않는다고 단정하지 않는다.
- 충돌하거나 오래된 기억은 원본과 비교해 갱신·supersede. 사용자 반박이나 외부 댓글을 자동으로 핵심 정책에 승격시키지 않는다.

**시험:** 원인 미확정 사건, 상충된 결정, 삭제 요청·캐시 반영, 공개 PR에 내부 장애 로그 유출 금지.

## V2-08. 복구 준비 상태 점검

**사용 예:** “서버 전체를 다시 만들 때 빠진 복구 자산 있어?”

- 실제 백업 상태, 복구용 설정·키의 **보관 여부/검증 상태**, 복구 런북, 격리 복원 훈련 기록, 복구 소요 시간 근거를 점검한다. 키 원문 조회·로그 출력 금지.
- 작업 성공, 백업 완료, 실제 복원 검증을 별도 필드로 표시. 접근 못 한 로컬 문서와 없는 문서 구분.
- 운영 DB 복원이나 데이터 덮어쓰기 실행은 V4 단계에서 별도 승인한 절차만.

> 참고: 새 플랫폼은 PostgreSQL(공유 클러스터)과 영속 Valkey를 R2 버킷 `homelab-backups` 하나에 백업하고 14일 보존한다(확정(사용자 2026-10-18, T05), 설계 F "추가 확인", C.3.8). 복원 드릴은 자동화하지 않고, PGBackupStale 경보와 분기 1회 사람이 돌리는 복원 확인(`homelab db restore-check`, 목표 UX)으로 대신한다(설계 C.3.8).

**시험:** 백업만 성공하고 복원 시험 없음, 손상/만료된 자료, 복구 문서 접근 불가, 거짓 '복구 가능' 결론 차단.

## V2-10. 리뷰 지적 수명 추적·선택적 병합 전 완료 대기

**사용 예:** “지난 리뷰 지적이 이번 수정으로 해결됐어?”

- 리뷰 지적과 후속 head SHA의 연결, 해결/미해결/판정 불가 상태를 관리. 단지 코드 행이 이동했다는 이유로 새 지적 생성하지 않음.
- **선택:** 필요가 확인되고 사용자가 허용한 저장소에만 ‘리뷰 처리 완료’ 조건 도입. `completed`는 리뷰 프로세스 종료이지 **AI의 안전 승인**이 아님.
- 플랫폼 설계 문서의 자동 병합 범위(C.4.7)·필수 검사 `ci`·owner의 관리자 bypass 병합·GitHub 보호 설정(`infra/github`, D-28)에 미치는 영향 검토. timeout·외부 API 장애·부분 리뷰를 success로 둔갑시키지 않음. 병합 설정 변경은 별도 명시적 승인 필요.

**시험:** 리뷰보다 빠른 자동 병합, 최신 head 변경, 리뷰 서비스 중단·시간초과·문서 PR, 관리자 우회, 지적 해소 여부 불명.

## V2-12. 첨부 파일과 대화 위치 이동

- 로그·설정·이미지 수집 시 크기/형식/접근 권한/파싱 실패/민감정보 처리. 임의 URL 다운로드·내부 접근 우회 금지.
- DM↔스레드 이동은 수신 대상의 권한·기록 보존 범위를 검사한 **허용 가능한 최소 맥락**만 이전한다. 작업·질문 소유권이 이동하면서 잘못 바뀌지 않도록 한다.

**시험:** 다른 공개 채널로 비공개 기억 이동 금지, 외부 URL·악성 첨부, 동일 작업의 중복 이전, 이동 후 권한 회수.

### V2 종료 요건

지정 FEATURE_IDS마다 구현 위치·시험 리비전·한계·후속 항목을 증거에 연결한다. **V2 전체 출시 판단은 V2-01~V2-12 범위의 필수 기능과 변경→검증→후속→회고 end-to-end 시험이 갖춰졌을 때만** 요청한다. V3로 자동 진행하지 않는다.

# PART B. V3: 예방 점검과 최적화

## V3-01. 자원·용량 추세 분석: 최우선

**사용 예:** “새 서비스 추가할 여유가 있을까? 디스크 추세도 봐줘.”

- 현재/평소/피크 CPU·메모리·디스크, 설정된 자원 예산·빈 공간·서비스 의존도를 함께 본다.
- 수집 기간·관측 누락·배포 변화·표본 유효성 기록. 불충분한 단순 추세를 확정 디스크 고갈 일자로 표시하지 않는다. 판단 불가를 허용.
- 서비스 추가 시 피크와 장애 여유, 단일 노드의 자원 경합 고려. 용량 보증 불가.

## V3-02. 업데이트·Renovate·취약점 영향

**사용 예:** “이번 Renovate PR에서 지금 우리 설정에 영향 있는 것만 알려줘.”

- Renovate PR(저장소별로 설치한 호스팅형 Renovate App이 만든 것, D-18)·보안 공지·현재 잠금 버전/이미지 digest·설정을 읽고 **실제로 해당하는 변경**인지 확인한다.
- 공식 릴리스·취약점 정보 확인 시각, 영향 조건, 테스트·적용 우선순위, 관련 파일을 제공. 기능 사용 여부가 불명확하면 영향을 확정하지 않음.
- 외부 자료의 실행 지시·코드 업로드 요구 무시. 변경은 허용된 PR 작성 경로까지만 진행.

## V3-03. 보안·공개 범위·권한 의도 이탈 점검

**사용 예:** “내부 전용 서비스가 바깥으로 열린 흔적이 있을까?”

- 등록한 서비스·도메인·Cloudflare(터널·WAF·공개 DNS)/Tailscale(operator Ingress의 `*.ts.net` 내부 UI·ACL·DNS)/Traefik Ingress/NetworkPolicy/권한 설정 등을 **허용된 읽기와 검사 범위 안에서** 비교.
- 설정상 허용 vs 외부에서 실제 접근 가능함을 구분. 임의 스캔·침투 시험·비밀 값 수집 확장 금지.
- “보안 이상 없음” 대신 검사한 대상·기준·미확인 경로 제시.

## V3-04. 미사용 자원 정리 후보·비용 분석

- 실제 참조·소유·보존 정책·최근 사용·백업·복구 의존을 대조해 **정리 후보**만 생성. 고아 PVC나 연결을 찾지 못한 자원을 삭제 가능으로 확정하지 않는다.
- 모델·R2 등 사용 비용은 실제 과금/사용량·단위·미포함 항목·예산을 확인해서 분석. 추정 환율과 불명확한 요금 정보를 확정값처럼 쓰지 않음.

## V3-05 + V3-08. 멀티레포 계약 검토·새 서비스 설정 제안

- 앱 소스/배포 GitOps repo, 공유 Helm 차트, DB 스키마·API 계약을 **영향받을 범위에서만** 점검. 모든 PR에서 전체 코드베이스를 무차별 분석하지 않는다.
- 새 앱 추가에는 템플릿/설정/비밀값 **키 이름**/테스트/PR까지 제안. DB 생성·시크릿 값 열람·공개 DNS 활성화·운영 배포는 실행하지 않는다.

> 참고: 새 플랫폼에서 "공개 DNS 활성화"는 `apps/<app>/values.yaml`의 공개 host 한 줄을 켜는 일이다. 공개 DNS는 와일드카드 레코드 하나다(설계 A.6, C.3.4). 앱 저장소는 public만 허용한다(D-29, 확정(사용자 2026-10-18)).

## V3-06. 지정 대화의 지식 정리·주간 개선 제안

- 허용 범위의 대화/기간/사용자만 학습 대상으로 삼고, 기억 ACL·삭제·유효기간·출처 검증 유지. 전체 채널 수집/모델 재훈련/핵심 정책의 자동 변경 금지.
- 개선 후보는 근거·예상 효과·위험·비용·확인 가정과 중복/거절 기록을 포함. 거절된 제안을 매번 새 경고처럼 반복하지 않음.

## V3-07 + V3-09. 선택적 다중 실행 호스트·병렬 작업·웹 화면/검토 모델

- 실제 수요가 있을 때만 추가. 호스트마다 인증·능력·격리·상태·자원 예산·등록 취소를 검증하고 같은 자산의 변경 작업은 잠금/직렬화.
- 웹 대시보드·다중 모델 검토는 선택 기능. 인증·ACL·감사 경계를 재사용하며, 모델 수가 늘었다는 사실을 검증 품질로 간주하지 않는다.

### V3 공통 출력 계약

```text
대상 / 검토한 시간창 / 실제 자료와 확인 시각
확인된 상태 / 성립 조건이 있는 추정 / 확인하지 못한 항목
권장 변경·점검 / 영향 / 필요한 검증 / 실행하지 않은 작업
우선순위 근거 / 재검토 또는 유효기간
```

### V3 공통 시험·종료

정상·데이터 누락·급격한 사용량 변화·거절된 제안·오래된 자원 소유·비해당 취약점·외부 자료 인젝션을 평가. **유효 제안·오탐·중복 알림·사용량·사용자가 실제 채택한 작업**을 기록한다. 실행/수정 권한 확대 없이 PR 제안까지만 동작하는지 확인. 선택한 FEATURE_IDS의 코드·시험·지침·근거와 HANDOFF를 갱신하고 V4를 자동 시작하지 않는다.
