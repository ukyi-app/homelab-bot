# PART A. V4: 사람이 승인한 정확한 운영 작업

## 1. 목표·운영 원칙

**제품 약속:** “사람이 정확한 변경 내용과 영향을 보고 승인하면, 제한된 실행기가 등록된 절차를 수행하고 사후 확인한다.”

- V4는 **저위험의 등록된 운영 절차 한 가지**부터 시작한다. 예: 사전 정의된 대상/허용 조건의 유지보수 작업. 운영 환경에 영향을 주는 구체적 절차는 사용자가 지정하거나 안전성 분석 후 별도로 승인받는다.
- 사용자가 GitHub에서 PR을 직접 병합하는 흐름이 이미 충분한 승인이면 Discord 승인 화면을 추가하는 것이 오히려 복잡할 수 있다. 정확한 플랫폼 승인 경로(자동 병합 조건 밖 PR은 사람이 검토 후 병합한다. owner PR은 관리자 bypass 병합, 봇·Renovate PR은 code owner 승인. 설계 C.4.7)를 재사용하는 대안을 평가한다.
- 플랫폼의 owner 로컬 실행 경로(Terraform apply와 `homelab github apply`, `homelab data purge`·`homelab db restore`)·GitOps(Argo CD)·GitHub App 권한 계약(`homelab-deploy`·`homelab-merge`, 봇 App, ruleset)을 **실제 코드/문서와 대조**한다(기준은 설계 C.3.9·C.4.7·C.4.9·C.5.5·C.8). owner의 PAT·인프라 쓰기 키(Terraform 자격, 배포·병합 App 키)를 모델 작업자에 주거나 워크플로의 작성자·트리거 확인(`deploy-merge`의 조건 1, ci의 workflow-guard)을 무력화하지 않는다.
- 범용 특권 셸 금지. 실행기에는 등록된 목적별 함수만 공개하고, 대상·입력·상태·시간·동시 실행을 제한한다.
- 운영 자격을 가진 실행기와 모델 추론 환경은 별도의 신뢰 경계로 유지한다. **승인 데이터는 모델 문장이나 Discord 단순 버튼 응답만으로 확정하지 않는다.** 서버가 actor·권한·정확한 작업·현재 상태를 검증한다.

**코드에서 강제할 규칙:**

1. 승인 전에 실제 절차·대상·입력·버전·환경·영향·사후 확인을 제시한다.
2. 승인자 자격·승인 경로의 진위를 확인하고 위조 actor·낡은 질문·재사용된 승인·중복 버튼을 거부한다.
3. 입력/커밋/정책/대상/중요 현재 상태가 승인 후 변경되면 **새 승인**이 필요하다. 재점검 없이 오래된 ‘응’ 사용 금지.
4. 승인 시각·만료·사용 가능 횟수와 취소·거절·소비 기록을 저장한다.
5. 실제 실행 직전에 권한·사전조건·환경 잠금·중복 동작·리비전을 재확인한다.
6. 실행·API 응답·배포 수렴·사용자 기능 검증을 별도 단계로 관측한다. 실패/외부 결과 `unknown`을 성공으로 처리하지 않는다.
7. 실행 성공 후 응답 유실이 발생하면 먼저 실제 외부 효과를 대조하고 재시도 여부를 결정한다. 무작정 같은 변경을 반복 실행하지 않는다.
8. 비상 중단은 신규 실행을 막는다. 이미 진행된 외부 동작이 중단/되돌려졌다고 거짓 보고하지 않는다.

## 4. 실제 운영 위험을 특별 취급

- **배포·롤백:** 단일 노드, DB 마이그레이션(Argo CD Sync hook Job, 이미 self-migration인 앱은 그 방식. 특히 contract 단계의 스키마 수축)이 이미지 롤백을 불가능하게 할 수 있다. 사전 확인과 사후 검증을 별도로 기록. 이미지 롤백과 DB 복원의 구분은 설계 C.4.9.
- **복구 훈련:** 데이터 복사 경계, 비운영 네트워크, 대상 스토리지, 자료 보존, 리소스 예산, 청소/증거를 정의. 운영 DB 덮어쓰기 금지.
- **리소스 정리:** 참조를 확인 못 했거나 고아 자산이라는 이유만으로 삭제하지 않음. 원래 보존 목적·백업·정책까지 확인.
- **고위험 행위:** 실제 운영 DB 복원·대량 삭제·공개 노출·권한 확대는 일반 저위험 승인에 섞지 않는다. 별도 위험 검토와 명시 승인 없으면 수행하지 않음.

# PART B. V5: 관찰 모드 후 제한적 자동화 (선택)

## 6. V5 진입 조건

- V4 승인형 실행 절차가 실제 운영에서 필요했고, 각 절차의 정상·실패·중단·승인 이력이 존재.
- 특정 반복 업무가 **조건·대상·빈도·영향이 정형화되어 반복**됐다는 근거가 있다.
- 사용자가 해당 절차의 **사전 승인 정책**에 명시적으로 동의하고 운영 중 중단/회수 수단을 갖췄다.
- 위 조건이 부족하면 V4를 유지하는 결론을 허용. **V5 미구현은 실패가 아님.**

**V5는 “AI가 스스로 좋은 해결책을 찾았으니 실행”하는 기능이 아니다.** AI는 설명·분석을 할 수 있지만 **실행 가능 여부는 사람이 승인한 정책과 현재 측정 가능한 조건**으로 판정한다.

## 7. V5 구현 순서

| ID | 기능 | 지켜야 할 제한 |
|---|---|---|
| **V5-01** | **관찰 모드(shadow/observe-only)** | 실제 실행 없이 ‘실행했을 작업’·근거·대상·조건을 기록해 사람의 결과와 비교 |
| **V5-02** | 알려진 장애에 대한 등록 대응 | 정확한 경보 조건·절차·대상·횟수·쿨다운·정지 조건 안에서만 |
| **V5-03** | 일부 정형 PR 자동 병합·배포 | 허용 변경 유형·파일·게이트·실제 리비전·보호 규칙 확인; AI 리뷰는 안전 승인 아님 |
| **V5-04** | 임시 비운영 자원 정리 | 생성할 때 명시한 소유·만료·보존 정책과 참조 상태 확인 |
| **V5-05** | 정기 격리 복구 훈련 | 허용된 별도 환경·저장소·자원 예산·데이터 접근·정리 조건 |
| **V5-06** | 정책 만료·중지·V4 복귀 | 중요한 상태 변경/반복 실패/관측 불명/예산 초과 시 자동 중지 |

**기본은 V5-01만 구현해 평가한다.** 안전·품질 자료가 충분하지 않으면 나머지를 활성화하지 않는다.

## 8. 사전 승인 정책 계약

```text
policy_id, policy_version, approved_by, approved_at
allowed_operation, allowed_targets, allowed_inputs
trigger_conditions, required_evidence, evidence_freshness_limit
preconditions, permitted_environments, concurrency_limit
per_target_cooldown, max_executions_per_window, usage_budget
verification, stop_conditions, expiry, fallback_to_human
status: observe_only | enabled | paused | revoked
```

**정책 강제:** 실행 직전 신선한 근거·대상·입력·리비전·권한·선행 상태를 재확인. 핵심 정책은 일반 대화·기억·PR 댓글로 수정 불가. 사람이 승인한 정책 버전을 유지하고, 자동화가 스스로 범위를 넓히지 않게 한다.

- **장애 자동 대응:** 반복 재시작 루프, 복합 장애, 관측 불명, 최근 변경·데이터 위험이 나타나면 자동 실행 중단. 미리 등록하지 않은 새 명령은 제안만.
- **자동 병합:** 플랫폼의 자동 병합 경로(배포 digest PR만, `deploy-merge`와 `homelab-merge`, D-07)와 중복 제어하지 않음. 검사 대상 실제 배포 리비전이 바뀌면 새 결과로 검증. 시크릿·정책·권한·DB 스키마 변경 등은 기본 제외하고 별도 정책 없으면 금지.
- **임시 자원 청소:** 단지 조회 기록이 없다는 이유로 공유/운영 자원을 삭제하지 않음.
- **복구 훈련:** 운영 네트워크·실제 사용자 데이터·가동 서비스에 영향을 주지 않는 격리 환경만.

## 9. V5 관찰·활성화·중지 시험

- 관찰 모드에서 **거짓 경보, 중복, 오래된 리비전, 데이터 부족, 사고 가능성, 실제 사람 판단과 차이**를 기록.
- 사례 수·관찰 기간·통과 목표는 환경에 맞게 제안하고 사용자와 합의. 임의의 숫자를 보편 안전 보증으로 주장하지 않음.
- 정책 변조, 권한 철회, 토큰 만료, 무한 반복, 중복 PR/배포, 정책 만료, 최신 상태 변경, 예산 초과, `unknown` 결과의 자동 재시도 거부 시험.
- 신규 자동화 중단 및 **V4 승인형 경로로 복귀**하는 흐름을 실증. 일시 정지된 정책의 자동 재활성화 금지.
- 활성화되지 않은 정책은 ‘계획됨’ 또는 `observe_only`로 표시. 실제 운영 동작이 없으면 자동화 완료를 주장하지 않음.

**산출물:** 버전 고정 정책과 승인 증거, 관찰 보고서, 제한 실행 테스트, kill switch·회수·재활성화 승인 런북, 잔여 위험, HANDOFF. 다른 절차로 정책을 자동 복제하거나 권한을 확대하지 않는다.

## 10. 마지막 확인: 전 버전 공통의 금지선

모든 대화 수집, 모든 개인 터미널 제어, 모델의 스스로 핵심 정책/권한 변경, 임의 해결 명령 자동 복구, 범용 관리자 셸, 테스트 없이 자동 병합·배포·데이터 변경은 V5에서도 비목표다. 플랫폼의 GitOps(Argo CD)·CI(`ci`)·관측 도구(D-09)를 재사용하고, 한 단계의 편의 때문에 신뢰 경계를 무너뜨리지 않는다.
