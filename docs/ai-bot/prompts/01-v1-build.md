```text

봇 문서(00-start.md, 01-v1-build.md, 04-audit-handoff.md)는 ukyi-app/homelab-bot 저장소의 docs/ai-bot/prompts/에 있다.

spec.md나 platform/design.md를 읽지 못하면 미확인으로 채우지 말고 멈추고 보고하라.

입력/허용 행동/금지 행동/완료 증거/실패 상태·재시도 정책을 코드와 시험에 반영하라.

근거 없는 성공·지원하지 않는 세션 제어·테스트 미실시를 완료라고 주장하지 마라.
04-audit-handoff.md 양식에 현재 단계 산출물·시험 리비전·미확인 사항을 남긴 뒤 중단하라.
```

## 1. V1에서 구현할 논리적 아키텍처

```text
 [Discord Gateway / Interactions]    [GitHub Webhook]    [플랫폼 Alertmanager 등]
              \                           |                        /
               └────────── [Inbound Adapters] ──────────────────────┘
                       서명·주체·설치·허용 목록·접근권한 검사
                                  |
                   [Durable Event Inbox + Job/Outbox Store]
                                  |
                    [Conversation / Job Coordinator]
                      ↙           |                ↘
           [Read-only Query]  [PR Reviewer]   [Codex Task Adapter]
                      ↘           |                ↙
                          [Evidence / Policy Validation]
                           ↙                  ↘
                      [Memory]             [Restricted Publishers]
                                            ↙                ↘
                                          Discord         GitHub
```

이는 **역할의 경계**다. 실제 서비스 수와 봇 내부 큐·런타임 구현은 DISCOVERY에서 비용·복구·격리 수준으로 선택한다. DB 인스턴스는 플랫폼 결정을 따른다(D-05, 확정(사용자 2026-10-18, T05): 공유 PostgreSQL 인스턴스 + 앱별 DB·역할, 봇 포함). 플랫폼이 제공하는 관측과 GitOps를 중복 개발하지 않는다(GitOps는 k3s + Argo CD, C-07. 관측 스택은 D-09, 확정(사용자 2026-10-18, T05): 옛 계열 최소 구성(설계 F D-09), 봇의 관측 읽기 자리는 Grafana Viewer. 자세한 것은 플랫폼 설계 문서(platform/design.md) F D-05·D-09). 공개 webhook 수신 경로와 홈랩 내부 조회 경로는 플랫폼 요구로 설계한다(spec §4.2, AC-P12). DISCOVERY는 플랫폼 설계 문서에서 그 경로를 읽고 실측해 봇 쪽 네트워크 경계를 정한다.

## 2. 공통 기반 요구사항 ID: F01~F09

| ID | 모든 V1 단계가 따라야 할 계약 |
|---|---|
| **F01** | 요청자·guild·채널·저장소·서비스 허용 목록, 최소 권한·권한 철회 즉시 반영 |
| **F02** | 영속 inbox/outbox/job, 의미적 중복 키, ACK 유실·역순/누락 이벤트 대조·복구 |
| **F03** | 비신뢰 자료와 실행 지침 분리; 작업 격리·운영/게시 자격증명 비상속 |
| **F04** | 비밀값 비수집, 원본 ACL·출력 대상 공개 범위 검증, 보존·삭제 반영 |
| **F05** | 동시성·실행시간·도구호출·재시도 제한, 작업 우선순위, 비상 중단 |
| **F06** | 작업 vs 전달 상태 구분, 감사·마지막 정상 수집 시각·모델 장애/관측 장애 구분 |
| **F07** | 영속 예약, 상태·기억 백업과 복구, 재시작 후 작업·알림 정합성 |
| **F08** | 입력/출력/증거/시험이 실제 변경 리비전에 결합; 기능·보안·리뷰 품질 평가 |

모든 외부 쓰기는 **“최종적으로 무엇이 바뀌는가?”**를 검사한다. 예를 들어 명령 이름이 PR 생성이어도 뒤에서 auto-merge나 배포가 수행되면 V1 변경 제안 경계를 넘어선다. 이런 경로는 V1에서 비활성화하거나 안전한 별도 제안 경로를 만든다.

## 3. STAGE=DISCOVERY: 먼저 조사하고 결정한다

**목표:** 실제 프로젝트와 외부 도구에서 가능한 기능을 조사해 V1을 구현할 수 있는 설계와 시험 계획 완성. 이 단계는 코드 구현이나 자격증명 변경이 아니다.

**질문(정보가 있으면 다시 묻지 말고 조사):** 질문 1·5·6은 플랫폼 설계 문서(platform/design.md)와 homelab 명세(spec.md)(§1 현재 상태, §4.5 현실 제약, §5 결정)를 먼저 읽고 답한다. 거기 답이 있으면 실측으로 확인만 한다.

1. 앱 코드 저장소, 홈랩 배포 설정 저장소, 각 저장소의 `AGENTS.md`·CI·앱 템플릿·운영 계약은? 배포 설정 저장소는 `ukyi-app/homelab`이다(C-01, C-07). 봇 코드 저장소는 `ukyi-app/homelab-bot`(public)이다(D-13, 확정(사용자 2026-10-18, T14)). 배포 설정은 homelab의 `apps/homelab-bot/`·`data/homelab-bot/`, namespace는 `app-homelab-bot`, Infisical 경로는 `/apps/homelab-bot/`(게시 서버)와 `/apps/homelab-bot/worker`(작업자)다. 봇 저장소는 public 앱 저장소라 코드·이슈·Actions 로그·이미지가 공개된다. 그래서 tailnet 이름, Tailscale IP 같은 D-23 금지 항목을 코드·로그·이미지에 두지 않는다(D-29, 확정(사용자 2026-10-18)). 저장소는 사람이 빈 public 저장소로 만들고 내용을 넣기 전에 하드닝한다. 플랫폼 등록은 T16b(실연동·첫 배포)가 `homelab app add`로 한다(플랫폼 설계 문서 C.8 "봇 저장소". T16의 T16a·T16b 분할은 §0 아래 "실제 티켓 순서와 완료 조건").
2. 제어 프로세스·영속 상태 저장·작업 실행기는 어느 호스트에 둘 것인가? 봇 전체 중단 시 외부 경보는? 서버는 NUC 한 대다(C-07 단일 서버, spec §4.5). 작업자 격리의 기본 방식은 설계 C.8 기본값으로 확정(사용자 2026-10-18, T05)됐다. 나머지는 D-15, 확정(사용자 2026-10-18, T15): NUC 클러스터 안이다. 게시 서버는 ns `app-homelab-bot`, 작업자는 ns `sandbox`의 상주 파드(동시성 1)이고, 라벨은 `homelab-bot`, 포트는 앱·작업자 8080, 경보 수신 8081이다. 작업자의 코드 읽기는 `codeload.github.com` 압축본만이다(§6 격리). 파드 방화벽(U13)이 안 되면 호스트 전용 UID + nft로 물러난다. 봇과 독립된 비AI 경보와 외부 생존 감시는 플랫폼 요구이므로(spec §4.2, AC-P11. ## 4. STAGE=FOUNDATION: Discord·작업·읽기 전용 조회 (R01~R07)

**핵심 흐름:** 허용된 Discord 스레드에서 “등록된 서비스 상태 알려줘” → 요청자·대상 검사 → 이벤트 저장 → 읽기 조회 → 근거와 미확인 사항을 올바른 스레드로 전달 → 재시작 뒤에도 작업·대화 상태 유지.

### 입력·허용·금지

| 항목 | 계약 |
|---|---|
| 입력 | 인증된 Discord 이벤트, 명시적 스레드 활성화·해제, 등록 서비스 조회, 플랫폼 관측 알림 |
| 허용 | 제한된 서비스/로그/메트릭 읽기, 대화·작업 상태 저장, 알림 중계 |
| 금지 | 미허용 대화 수집, 임의 셸, Secret 값 조회, 무단 재시작/배포/수정, 모든 알림의 무제한 AI 조사 |
| 완료 | 대상·시간창·출처·관측 시각과 사실/가설/미확인을 포함한 응답; 작업/전달 기록 일치 |
| 실패 | 데이터 조회 불가→미확인, 모델 장애→모델 실패, 작업 호스트 단절→unknown, 중복→같은 작업/전달로 대조 |

### 구현 세부

- **R01 스레드 구독:** 공식 봇 인증, 허용 사용자·guild·채널, 명시적 멘션/명령으로 시작, 이어지는 메시지 처리, 구독 해제·권한 철회 시 즉시 중단. Message Content Intent가 확보되지 않으면 명령/버튼 모드라고 명시. 스레드·DM 정보 혼합 금지.
- **R02 응답 적절성:** 이벤트 수신 확인은 AI 호출 전에, 이어지는 짧은 메시지 묶기는 설정 가능한 debounce로 처리. 취소·긴급 요청은 묶기 지연에서 제외. **수신과 응답은 별개**로, 불필요하게 끼어들지 않음.
- **R03 작업·대화 분리:** 대화는 응답을 유지하고 긴 작업은 별도 작업자로. 추가 조건 도착 시 안전한 지점에서 재평가하되 별도 실행을 일괄 취소하지 않음. 목록·취소 요청·실제 취소 확인·실패 재시도·세션 정리/재개 지원.
- **F02 영속 계약:** event/provider/actor/scope/time, job/type/owner/target/revision/budget/state/attempt, conversation/subscription, result/evidence/classification, delivery/outbox, schedule/timezone/next_run. 저장 후 응답, lease/heartbeat, 외부 효과 불명 재실행 금지, 장애 후 재조정. `exactly once`를 실측 없이 보증하지 않음.
- **R04 서비스 카탈로그:** 서비스 ↔ 소스 저장소 ↔ 배포 ↔ 내부/외부 도메인 ↔ 운영 문서. 등록/관측 불가 상태를 구별하고 데이터가 없다고 가상의 값을 채우지 않음.
- **R05~R06 읽기 어댑터:** 조회 메서드·허용 네임스페이스·시간창·응답량·쿼리 복잡도 제한. 사전 승인된 데이터 조회만; 내부 환경변수, Secret, 임의 ConfigMap·로그 전체 수집 금지. 사실/가설/미확인/권장 확인을 구분. “정상”은 현재 관측 증거 있을 때만.
- **R07 알림:** 플랫폼 Alertmanager 등(관측 스택 D-09, 확정(사용자 2026-10-18, T05))의 그룹화/중복 제거를 우선 재사용, 사건 스레드 연결. 기본 백업·인증서·예약 작업 메타데이터는 실제 조회 가능한 것만 사용; 복원 가능하다는 결론으로 확장 금지.
- **F05~F07 운영:** 대화 응답/장애/리뷰/배경 작업 우선순위, 자원 예산, 큐 적체·비상 중단, 상태·기억 백업 및 재시작 시험. 플랫폼의 비AI 알림 경로(D-10, 확정(사용자 2026-10-18, T05): homelab 알림용 Telegram 새 봇)는 그대로 두고 봇으로 대체하지 않음; 홈랩 전체 중단 알림은 플랫폼의 외부 생존 감시(AC-P11, D-10의 healthchecks.io)를 실측으로 확인했을 때만 범위에 포함.

> 참고: R04의 내부 도메인은 Tailscale operator Ingress의 `<서비스>.<tailnet>.ts.net`이다. `*.home.ukyi.app` 내부 이름은 두지 않는다(D-08, 확정(사용자 2026-10-18)). tailnet 이름은 봇 저장소의 코드·로그·이미지에 적지 않는다(D-29). 봇 파드의 인터넷 443 허용에서는 사설·tailnet 대역이 빠지므로, 봇의 조회는 이 이름이 아니라 클러스터 안 Grafana·Argo CD API와 읽기 전용 SA `bot-reader`로 한다(플랫폼 설계 문서 C.8).

**시험:** 권한 없는 사용자/서비스/채널/스레드, 권한 철회 후 조회; 중복·늦은 이벤트; 수신 ACK 유실; 재시작·lease 만료; 로그의 인젝션; 임의 셸/Secret 차단; 조회 미응답과 정상 구분; 작업 중 대화; 취소 요청과 실제 중단 구분; 예약·백업 복구·예산 상한.

**산출물:** 서비스/쿼리 어댑터, durable 상태·스키마, Discord 진입점, 대화/조사 런타임 지침, 시험 기록 및 인수인계. 실제 Discord 권한이 없다면 mock과 미실연동을 구분.

## 5. STAGE=PR_REVIEW: 전용 GitHub App 기반 자동 PR 리뷰 (R11~R12)

**핵심 흐름:** 허용 PR 생성/갱신 → 서명·설치·대상 검사 → 고정 비교 리비전 수집 → 별도 리뷰 작업자 분석 → 게시 직전 head 재확인 → GitHub `COMMENT` 리뷰 + Discord 요약. 플랫폼 병합 정책(자동 병합 범위 D-07, 확정(사용자 2026-10-18, T05): 배포 digest PR만 자동 병합, 서버 강제)은 변경하지 않음.

### 역할·권한

| 주체 | 가능 | 불가 |
|---|---|---|
| 리뷰 전용 App(기본) | 필요한 repo의 Metadata 읽기, Contents 읽기, Pull requests 쓰기(리뷰 게시), 실사용 시에만 Checks/Actions 읽기 | Contents 쓰기·관리 권한·워크플로 실행 권한 |
| 리뷰 작업자 | 허용 diff·문맥 읽고 구조화된 의견 생성 | GitHub 인증 키 보유, 외부 코드/훅 무단 실행, 승인·병합 |
| 제한 게시 서버 | 검증된 대상·리비전의 `COMMENT`와 허용된 요약만 게시 | `APPROVE`, `REQUEST_CHANGES`, merge, enable auto-merge, PR 자동 수정 |

`Pull requests: write` 권한은 `COMMENT` 단일 목적보다 넓을 수 있다. **서버 코드의 허용 API·이벤트 검사와 설치 저장소 제한**으로 범위를 더 좁힌다. 리뷰 App은 전용 키만 쓰고, 플랫폼의 다른 GitHub App이나 쓰기 자격과 공유하지 않는다. App 생성·설치는 별도 허가 없으면 모의 구현·설명까지만.

### 이벤트·신뢰·리뷰 데이터

- Webhook은 원본 바이트 기준 서명 검증 후 설치·저장소·주체 허용 확인. 표시 이름, PR 본문, 댓글의 지시문으로 권한 판단 금지. 접수 응답과 비동기 리뷰를 분리.
- 새 PR, 닫혔다 재개된 PR, draft 해제, 새 커밋 등을 실제 API 이벤트 계약에 맞게 처리. Draft는 기본 대기; 명시적 요청이면 예외. fork는 비신뢰 코드 실행 금지.
- 의미적 idempotency key는 `(repo_id, pr_number, head_sha, comparison_revision, review_policy_revision)` 등. delivery ID뿐 아니라 작업 세대 구분. 새 head/base면 이전 리뷰를 `superseded`로 처리.
- GitHub webhook 누락 복구: 열린 PR과 기존 처리 기록을 제한된 범위로 주기/수동 대조. 새 설치 직후 전 레포의 과거 PR을 무제한 리뷰하지 않음.
- 승인된 **기준 리비전**의 `AGENTS.md` 등 지침만 리뷰 기준으로 사용. PR이 변경한 지침·스킬·훅은 검토 대상일 뿐 상위 지침 아님. 코드 실행·의존 패키지 설치는 기본 금지.
- 파일 수·diff 크기·페이지 제한·생성 파일·바이너리·서브모듈·큰 잠금 파일·접근 불가 파일을 처리하며 검토 누락을 표시. 전체를 못 읽었으면 `partial`, 조회 실패면 `failed` 또는 `unknown`.
- 리뷰 기준: **실제 버그, 보안 경계, 데이터 손실, 호환성, 운영 계약, 재발 가능성 있는 테스트 누락**. 린트·스타일 취향 중복·근거 없는 사소한 의견은 제외. 프로젝트별 규칙(예: self-migration/expand-contract/멱등성/공유 차트)은 현재 소스에 근거가 있을 때만 적용.
- 지적에는 중요도·제목·파일/행·성립 조건·영향·증거·개선 방향. 확인 질문은 확정 버그와 구분. 임의의 확신 점수 금지. 리뷰 길이/인라인 상한은 대표 평가로 정하고 설정 없으면 자동 게시 거부.

> 참고: 앱 저장소와 봇 저장소는 모두 public이라 외부인도 PR·댓글을 남길 수 있다(D-29, 확정(사용자 2026-10-18)). 그래서 봇은 모델 호출 전에 이벤트의 `author_association`(OWNER·MEMBER·COLLABORATOR)과 설치·저장소 허용을 확인해, 외부인 PR·댓글이 모델 호출을 일으키지 않게 한다(플랫폼 설계 문서 C.8 webhook 수신 경로 행). 위 첫째 항목의 주체 허용 확인이 이 자리다. Renovate PR(D-18)·봇 작성 PR은 `author_association`이 `NONE`이나 `CONTRIBUTOR`로 찍혀 이 확인을 통과하지 못한다(T15 실측). 그래서 D-16 하위 결정으로 허용 봇 작성자 목록을 둔다(확정(사용자 2026-10-18, T15)). `pull_request.user.type`이 `Bot`이고 숫자 `user.id`가 목록에 있으면 통과한다. 초기 목록은 호스팅형 Renovate 봇과 D-24 App의 봇 사용자(생성 뒤)이고, 배포 갱신 App(`homelab-deploy`)·Codex Connector·옛 쓰기 App은 뺀다. fork PR은 빼고, 댓글 트리거는 `comment.author_association`을 보며 Bot 댓글은 무시한다. `CONTRIBUTOR`는 허용하지 않는다. 실제 ID는 Infisical runtime policy(키 이름 예: `review.allowed_bot_author_ids`)에만 둔다. 허용 작성자의 PR 본문도 비신뢰 자료로 다룬다.

### 리뷰 결과 계약(예시)

```yaml
review_job_id: string
repo_id: string
pr_number: integer
head_sha: string
comparison_revision: string
policy_revision: string
reviewed_at: timestamp
coverage:
  checked_files: []
  omitted_files_with_reasons: []
  limits_hit: []
checks: [] # 검사 명칭 / 리비전 / 실제 결과 / 링크 / not_run
findings: [] # severity, title, path, line, evidence, condition, impact, suggestion
open_questions: []
public_summary: string
output_classification: public_or_restricted
review_outcome: completed_or_partial_or_failed_or_superseded
```

게시 직전 실제 최신 PR/head/base·설치 권한·출력 공개 범위·diff 위치를 재검사한다. 게시와 마지막 확인 사이 경쟁은 완전히 제거할 수 없으므로 검토 SHA를 게시하고 이후 이벤트에서 오래된 결과를 대조한다. ACK 유실 시 기존 게시 여부를 조회하고 같은 내용을 중복 게시하지 않도록 함. **리뷰가 완료돼도 안전 보증이나 병합 승인은 아님.** 자동 병합이 리뷰보다 먼저 끝난 PR은 과거 리뷰로만 기록.

### 최소 리뷰 시험·품질 평가

- 알려진 정상 PR → 확정 버그 오탐이 없는지; 알려진 버그 PR → 근거가 정확한지; 호환성 사례 → 유효 지적인지.
- 서명 위조·미허용 설치·fork 실행·PR AGENTS 인젝션·게시 토큰 접근 차단.
- 중복 이벤트·새 push/base 변경·draft·닫힘·병합·App 제거·API 제한/중단.
- 큰 PR·부분 수집·바이너리 파일을 완전 검토/안전으로 표시하지 않음.
- 게시 성공/ACK 유실, 인라인 위치 무효, 리뷰 이벤트 자기 루프 차단. **봇이 작성한 PR 자체는 정상 리뷰**.
- `APPROVE`, `REQUEST_CHANGES`, merge, auto-merge, 수정 요청이 게시 서버에서 차단됨.
- 비공개 운영 자료가 공개 PR에 누출되지 않음.
- 평가셋으로 유효 지적·오탐·알려진 버그 누락·중복·잡음·시간·모델 호출량 기록. 작은 평가셋을 일반 정확도 보증으로 표시하지 않음. 기록 양식은 `04` §6.

**산출물:** App 설치·권한 안내(실제 설치 아님), webhook/리뷰·게시 어댑터, 구조화된 출력과 런타임 리뷰 지침, test fixtures·품질 평가, Discord 요약 경로, HANDOFF.

## 6. STAGE=CODEX_BRIDGE: Codex 작업·질문·완료 중계 (R03, R08~R10)

**핵심 흐름:** Discord에서 봇 소유 Codex 작업 시작 또는 **명시적으로 연결한 기존 작업** 조회 → 진행·질문/대기·완료 이벤트를 해당 대화로 전달 → 허용된 사용자 응답만 해당 질문에 중계 → 결과와 실제 증거 확인.

**먼저 능력 확인:** Codex/herdr의 현재 릴리스·설치 버전/인증/지원 플랫폼·CLI/API로 아래 추상 계약을 **실측 또는 제약 기록**한다. 이것은 실제 CLI 명령 목록이 아니다.

```text
capabilities()
start_task(project_id, trusted_policy_revision, task, isolation, budget)
attach_task(external_task_id, authorized_owner, scope)
read_status(task_id), read_events(task_id), read_final_result(task_id)
answer_question(task_id, question_id, answer, actor)
request_cancel(task_id), confirm_stop(task_id)
resume_task(task_id, verified_resume_state)
```

가능하지 않은 기능은 `capability=false`·제한 모드로 표시. 실험적 API를 무조건 안정 제품 경로로 사용하지 말고 실제 지원 및 대체·버전 고정·재접속 동작 확인. **모든 개인 터미널·별도 CODEX_HOME·인증 파일을 자동 검색·통합 제어하지 않음.**

| 처리 | 구체 요구 |
|---|---|
| **소유자 연결** | Discord 대화·actor·작업 ID·외부 세션 ID·실행 호스트·저장소·허용 능력을 영속 기록. 타인 작업 접근 차단. |
| **격리** | 신뢰 가능한 프로젝트 지침에서 시작하되 workspace 분리와 보안 격리는 별도. 개인 HOME 전체·운영 kubeconfig·SSH agent·GitHub 게시 자격 비상속. 격리 실행 공간은 플랫폼 요구이고(spec §4.2, AC-P12) 기본 방식은 설계 C.8 기본값으로 확정(사용자 2026-10-18, T05). D-15, 확정(사용자 2026-10-18, T15): 작업자는 NUC 클러스터의 ns `sandbox` 상주 파드(동시성 1)이고, 코드 읽기는 `codeload.github.com` 압축본만 한다(작업자 egress에서 `github.com`·`api.github.com`·gist 제외, 작업자에 GitHub 자격 없음). 받은 코드는 작업자가 `git init`으로 한 번 커밋해 `codex exec`의 Git 저장소 요구를 맞추고, diff는 base·head 압축본으로 만든다. push와 PR 생성은 게시 서버가 D-24 App으로 한다. 파드 방화벽(U13)이 안 되면 호스트 전용 UID + nft로 물러난다. 모델 인증은 작업자 전용 CODEX_HOME이다(D-14). |
| **질문** | `job_id + question_id + 질문 유형 + 생성/만료 시각 + 응답 가능 사용자` 결합. 중복·오래된 답변·다른 질문 응답 차단. |
| **승인 구분** | clarification과 tool approval 분리. V1 외 운영 실행·격리 해제 승인은 Discord 답변으로 새 권한 생성 불가. 무응답 자동 승인 금지. |
| **완료 기준** | terminal idle·프롬프트 표시만으로 완료 판정 금지. 최종 결과/생성 패치/검증 결과 대조. |
| **취소·재개** | `cancel_requested`와 `cancelled`, 단절 `unknown`과 실제 `failed` 분리; 기존 외부 효과 확인 전 무조건 재실행 금지. |
| **응답성** | 긴 로그는 빈도·길이 제한, 질문/개입 요청 우선 전달. 대화 추론이 바뀌어도 별도 작업을 무조건 종료하지 않음. |

**시험:** 명시적 연결·해제/허용 새 작업/작업 중 대화; 미등록 세션·타인 스레드 접근; 질문 재전송·중복·만료·권한 없는 답변; 가짜 로그 질문/완료/권한 확대; 호스트 단절·취소 불명·재개 미지원; 모델 세션에 인증키 유출 안 됨; 결과 상태와 Discord 전송 상태 따로 기록.

**산출물:** 어댑터 기능표·계약 시험, 권한 모델·상태 저장, 질문/완료 구조화 이벤트·지침, 연결 사용자 안내, HANDOFF. 실행 도구가 없는 경우 연결 mock까지만 완료로 표시.

## 7. STAGE=CHANGE_PR: 격리된 수정·독립 검토·PR 작성 (R13~R15)

**핵심 흐름:** 명시적 수정 요청 → 요청 범위/기준 리비전 확인 → 격리 작업공간에서 코드 수정·허용 테스트 → 별도 리뷰 세션이 결과 확인 → 게시 정책 검증 → 봇 브랜치·PR 작성(별도 허가 시) → 사람이 플랫폼 병합 정책(자동 병합 범위 D-07, 확정(사용자 2026-10-18, T05). 봇 변경 PR은 자동 병합 조건 밖이라 사람이 검토 후 병합)에 따라 병합한 뒤 **기본 읽기 전용 배포 상태 확인**.

**입력:** 요청자, 저장소, 기준 커밋, 목표/완료 기준, 허용 파일 경로, 금지 경로, 검증 명령 출처, 출력 공개 범위. 작업 중 새 조건·기준 이동을 기록하고 부정확한 재사용 방지.

- 작업자는 격리 환경에서 필요한 파일만 접근. 패키지 설치·테스트도 비신뢰 코드 실행일 수 있으므로 민감 환경변수·호스트 파일·네트워크를 제한. 변경 diff·시험 로그·증거·기준/결과 리비전을 구조화하여 반환.
- 이미 존재하는 테스트를 삭제/약화해 통과시킬 수 없다. 현재 적용된 프로젝트 지침과 V1 정책 충돌 시 승인 없이 예외 처리하지 않는다.
- 게시 서버는 **권한 있는 요청자, 허용 repo/봇 브랜치/파일 경로, 보호 파일, base/head 신선도, 시험 증거 일치, 공개 정보 범위, CI의 간접 효과**를 검사. main 쓰기·merge·auto-merge 활성화·workflow_dispatch·보호 규칙/시크릿 변경 거부.
- PR 생성 도구가 뒤에서 병합·배포를 일으키는 경로는 사용하지 않는다(§2 끝 문단). 자동 병합 범위(D-07, 확정(사용자 2026-10-18, T05): 배포 App이 만든 한 앱의 `image.yaml` digest·revision만 바뀐 PR)에 걸리는 PR도 만들지 않는다(T19). 봇 신원의 PR은 작성 주체 조건(조건 1)에서 빠져 자동 병합되지 않는다(플랫폼 설계 문서 F D-07, C.8). 별도 제안-only 경로를 구현·검증. GitHub 권한 자체가 merge를 허용할 수 있으므로 API·입력·실제 브랜치 보호를 조합해 강제.
- 봇 브랜치 push와 PR 작성에 쓰는 신원은 D-24, 확정(사용자 2026-10-18, T15): 봇 전용 쓰기 GitHub App이다. 권한은 Contents write + Pull requests write + Metadata read이고 Workflows·Actions·Administration·Issues는 없다. webhook은 끄고 선택 저장소에만 설치하며, 작업마다 저장소 하나로 좁힌 1시간 토큰을 쓴다. 병합 API·`/merges`·`repository_dispatch`·update-branch·GraphQL 병합은 권한으로 못 막으므로 게시 서버의 허용 목록이 막는다. 봇은 `.github/workflows` 변경 PR을 만들 수 없다(범위 축소). 토큰 분리, ruleset E 여부, App 이름·설치 저장소는 T19에서 정한다(미정). 리뷰 App과는 다른 신원이다(§5의 리뷰 App은 Contents 쓰기 불가).
- 작성 세션과 **다른 리뷰 세션**을 사용해 원래 요청·실제 diff·허용 기준 지침·시험 결과를 검토. 작성자의 '안전하다'는 문장은 증거가 아님. 새 diff에 이전 테스트·리뷰 자동 재사용 금지.
- 필수 시험 실패·근거 있는 고위험 지적은 숨기지 말고 사용자에게 표시. 정책이 허용하면 명시적 **Draft PR**로 공개 가능하나 성공 검증으로 표기 금지.
- 이미 존재하는 봇 PR, ACK 유실, branch 충돌, 사람의 커밋 추가 시 대조. 다른 사용자의 커밋을 덮거나 force push하지 않음.
- **R15 읽기 확인:** 병합한 PR head/merge commit/배포 설정/이미지 상태를 구분하고, 허용된 서비스의 목표 버전·Argo/Kubernetes 상태만 기본 확인. 읽기 전용 계정은 플랫폼 요구다(spec §4.2, AC-P12). 기능·DB 쓰기·성능 검증과 자동 rollback은 V1 범위 밖.

> 참고: Argo CD는 공개 webhook 없이 60초 폴링으로 Git 변경을 읽는다(`timeout.reconciliation: 60s`, `timeout.reconciliation.jitter: 0`. 확정(사용자 2026-10-18, T05), 설계 F "추가 확인"). 그래서 병합 직후에는 Argo CD가 아직 새 리비전을 읽지 않았을 수 있다. R15의 배포 확인 대기는 이 주기를 감안해 정한다.

**시험:** 격리 수정→시험→별도 검토→허용 PR; 보호 파일/main/auto-merge/dispatch 차단; 시험 미실행·실패·리비전 불일치; 기준 이동/충돌/사람 커밋; 악성 설치 스크립트의 토큰 접근 차단; 게시 ACK 유실·중복 PR; 내부 데이터의 공개 PR 유출 금지; PR 게시·병합·기본 배포 확인의 단계별 상태 분리.

**산출물:** 작업자 지침/구조화된 변경 결과, 제출 정책과 게시 API 계약, 독립 검토 결과, 읽기 전용 배포 확인, 시험 및 HANDOFF. 실제 시험 PR·댓글도 별도 허가된 자산에만.

## 8. STAGE=MEMORY_BRIEFING: 출처 기반 기억·일일 브리핑 (R16~R18)

**핵심 흐름:** 허용 문서·선택 대화·실증된 작업에서 중요한 지식을 출처와 함께 저장 → 다음 세션에서 ACL로 검색 → 수정·삭제·충돌 정리 → 예약 시각에 현재 상태를 조회하고 브리핑 → 재시작 이후 중복·누락 처리.

### 기억 분류와 최소 스키마

- 지속 구성·운영 계약: 현재 출처·확인 시각.
- 운영 결정과 이유: 결정 주체·시점·적용 범위.
- 장애·조치: 사실·가설·미확정 원인 분리.
- 개인 선호·일시 지시: 대상 사용자·유효기간·종료 조건.

```text
memory_id, kind, statement_or_summary
source_refs[], source_revision_or_observed_at, created_at, updated_at
scope(user/guild/channel/repo/service), access_scope, output_classification
valid_from, expires_at_or_recheck_condition
status(candidate/active/superseded/deleted)
replaces[], conflicts_with[], correction_reason
```

**규칙:** 출처 링크의 존재만으로 정확성 보증하지 않음. 근거 없는 것은 candidate/보류. 원본 접근 불가 자료 저장 금지. 과거 상태 대신 현재 조회 우선. 검색 전 ACL 필터. 정책·권한·승인 규칙을 일반 기억으로 변경 불가. 로그/댓글의 악성 명령을 학습한 핵심 정책에 반영 금지.

명시적 수정·삭제·저장 제외를 지원하고 캐시·색인·파생 요약에 반영. 백업이나 이미 게시된 외부 메시지의 즉시 삭제를 거짓 약속하지 말 것; 삭제 표식과 복원 시 반영 정책 기록. 세션 정리 시 진행 작업·미답 질문과 구독 상태를 durable store에 남기고 요약만으로 실행 상태를 복구한 척하지 않는다.

> 참고: 봇 DB는 공유 PostgreSQL 인스턴스에 있고(D-05), PostgreSQL 백업은 R2 버킷 `homelab-backups` 하나에 14일 보존한다(확정(사용자 2026-10-18, T05), 설계 F "추가 확인", C.3.8). 삭제한 기억도 백업 보존 기간 동안 백업에 남을 수 있으므로, 삭제 표식과 복원 시 반영 정책은 이 보존 기간을 기준으로 적는다.

**일일 브리핑:** FOUNDATION의 예약 기반 재사용. 시간대 기본 `Asia/Seoul`이나 **발송 시각·대상은 실제 설정**으로 정하고 누락 시 자동 발송 안 함. 확인이 필요한 문제·중요 변화·승인/질문 대기·작업 상태 위주. 백업 실패·인증서·예약 작업은 실제 접근 가능한 데이터만. 읽기 불가→마지막 정상 수집 시간 및 미확인 표시. 복원 검증은 백업 성공과 다름. 지난 며칠 분을 재시작 후 한꺼번에 전송하지 않고 최신 요약+누락 표시 정책 적용.

**시험:** 출처 누락·오래된/충돌 기억·일시 지시; 권한 회수 및 다른 채널 누출; 프롬프트 인젝션/핵심 정책 변경 차단; 수정·삭제·색인·복원; 세션 정리 후 재개; 예약 중복/시간대/재시작/모델 장애/전달 실패; 관측 데이터 없는 정상 주장 차단.

**산출물:** 기억/검색/수정 스키마·런타임 지침·ACL·삭제·보존 정책, 브리핑 작업과 시험, HANDOFF.

## 9. STAGE=RELEASE_AUDIT: V1 통합 검사 및 파일럿 판정

이 단계의 기본 MODE는 **`audit`**이다. `04` §1 감사 프롬프트로 `04` §4의 V1 수용 시험 30개 전체를 적용하고 `F01~F09`, `R01~R18`의 구현 위치·검증 증거·환경·리비전·미확인을 빠짐없이 추적한다. 이전 세션의 완료 주장을 코드와 실행 증거 없이 받아들이지 않는다.

**최소 end-to-end 흐름:**

1. Discord 요청 → 서비스 상태·근거 답변 → 구독/세션 정리 후 맥락 유지.
2. GitHub PR → 최신 리비전 리뷰 → `COMMENT`만 게시 → Discord 핵심 요약.
3. Codex 작업·명시적 연결 → 질문 → 사용자 답변 → 최종 산출물·검증 → 결과 전달.
4. 코드 수정 요청 → 격리 변경·시험·독립 검토 → 제안 PR → 기본 배포 상태 **읽기** 확인.
5. 운영 결정 저장 → 출처 검색·수정·삭제 → 예약 브리핑 → 재시작 복구.

**보안/장애 시험:** 미허용 actor·repo·스레드, 위조 webhook, 비신뢰 문서/코드의 명령, 작업자 자격증명 노출, GitHub APPROVE/merge/auto-merge/dispatch 차단, 내부→공개 자료 유출, 새 head/base·병합 선행, 중복/ACK 유실, 모델/DB/실행기 단절·unknown, 질문·취소 수명, 비용/알림 폭주, 상태·기억 백업 복원과 삭제 적용. 코드와 승인된 시험 자산에만 외부 시험.

**리뷰 품질:** 정상 PR·알려진 버그·문맥 필요한 호환성·검토 불가 파일·악성 지침·변경 도중 PR의 결과를 평가. 유효 지적·오탐·누락·중복·스타일 잡음·지연·호출 예산을 기록하고 **마케팅용 일반 정확도로 과장하지 않음**. 기록 양식은 `04` §6.

### V1 출시 판정(다음 중 하나)

`NOT_READY`, `LOCAL_VERIFIED_INTEGRATION_PENDING`, `READY_FOR_SCOPED_PILOT`, `V1_ACCEPTED`.

각 판정의 정의와 기준은 `04` §9다. V1→V2 전환 기준도 `04` §9에 있다.

**산출물:** `V1_RELEASE_REPORT.md`, 요구사항/시험 추적표, 잔여 위험·권한표·연동/키 회전/비상 중단/복구 지침, HANDOFF. 운영자 수용을 검토자가 대신 선언하지 않는다. **V2는 자동 구현하지 않는다.**
